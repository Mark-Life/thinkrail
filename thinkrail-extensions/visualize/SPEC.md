## Responsibility

The ThinkRail halves of the `visualize` tool. `./server` composes the portable capability
([[module-pi-visualize]]) with the **strict** mermaid validator the browser renderer agrees with; `./web`
is the props-driven presentation. The tool name joins the two without a wire change.

## Boundary

Two entrypoints and no root barrel. `@thinkrail/ext-visualize/server` default-exports
`defineServerExtension({ name: "visualize", title, description, sessionExtensions })`: one per-session
factory that registers `createVisualizeExtension({ validateMermaid, checkFile, mockupGuideline })`
and writes the theme file — no children, no skill packages — and may import `extension-api/server`,
`@thinkrail/pi-visualize`, `mermaid`, `linkedom`, and `node:fs`/`node:path`. `@thinkrail/ext-visualize/web` default-exports a `defineWebExtension` descriptor plus
named `MermaidView` for fenced mermaid in chat markdown, and consumes `extension-api/web`, per-file UI
primitives, `@thinkrail/resource-renderers` (`ResourcePreview` and the host seam), contracts,
`@thinkrail/locales/react` for its strings (`visualize.*` keys), React and
Remix Icon. Neither half imports the other, app/host internals, or (web)
any pi package; the browser loads `mermaid` lazily inside the renderer, never in the eager entry chunk.

## Strict validation (server)

The validator is the one injected through the pi package's `validateMermaid` seam, which **replaces** the
package's best-effort `lovely-mermaid` probe; the package still owns shape checks, empty-source rejection,
source enumeration and the field-specific diagnostic. The guarantee is **syntax parsing by the exact
`mermaid` version the web renderer uses** (catalog-pinned), not SVG/layout success — the renderer keeps
its defensive fallback.

- `mermaid` needs browser globals while its parser initialises and DOMPurify needs a real `document`
  for flowchart/class/state/gantt/mindmap (verified under Bun), so `linkedom` is required, not optional:
  a lightweight DOM exists only during the lazy `import("mermaid")`, and the previous `window`/`document`
  descriptors are restored in `finally`.
- `mermaid.parse` calls are serialised through a promise tail stored on the mermaid instance (so every
  loaded copy of this module shares it) because mermaid resets shared configuration per parse.
- Invalid syntax surfaces as the package's `isError` tool result asking the model to correct and retry;
  the extension injects no prompt and forces no retry.

The factory is composed per parent session (`sessionExtensions`) so file previews use the host's
`session.workspaceFiles` ([[submodule-server-extensions]]), shared with ask-user-question instead of copied:
a path must be relative, stay inside the session cwd (lexically and after resolving links, with the host
read guard's containment rule, so `..draft.html` is a name and not a parent), name a regular file and stay
out of `.git`, else the tool result asks the model to write it first — the same paths the host's
`fs.readFile` then serves, so the card never reports what the tool accepted as unreadable. `scratchDir` is
`.thinkrail/context/mockups/`, inside the host's gitignored scratch dir, so mockups never become project
changes.

## Mockup theme file and guideline (server)

`server/generated/thinkrail-theme.css` is generated by `apps/web`'s colour pipeline (`colors:generate`,
drift-checked by `colors:check`; [[web-color]]): the palette, ANSI colours, appearance effects and every
semantic role for the bundled Light theme, Dark under `prefers-color-scheme: dark`, and an `html` base, all
inside `@layer thinkrail-theme`, so any declaration in the mockup wins, layered or not, as in the app. That
holds for a layered author rule only when the link comes before the mockup's own styles (the first layer
declared has the lowest priority); the file's header says so. It lives in this package because the server half may not import `apps/web`. It is
imported as text (`with { type: "text" }`), so the CLI binary and the desktop artifact embed it with no
file lookup at runtime. Before every agent turn (`before_agent_start`, so it exists before the agent writes
a mockup and returns if deleted) `writeThemeFile` puts it at `<scratchDir>thinkrail-theme.css` in the
session cwd. It writes only when `<cwd>/.thinkrail/context` already exists as real directories (the host
seeds it with its `.gitignore` when a chat starts), so it never creates an un-ignored tree; otherwise it
skips. It refuses a scratch dir with a `.` or `..` segment before it touches the disk, `lstat`s every
segment before any `mkdir`, refuses a symlinked segment, creates only the `mockups` leaf, refuses a target
that is not a regular file, and rewrites only when the content differs. Together the first three keep the
write inside the workspace, so there is no separate resolved-path check. A failed write is ignored: the file only
helps the agent and the user see a mockup outside the app, and a broken turn would cost more. In the app
the link never loads (the themed frame removes it, the scripted frame's CSP refuses it) and the live theme
replaces it ([[module-resource-renderers]], *Themed frame* and *Scripted frame*).

`guidance.ts` supplies the pi package's `mockupGuideline` clause. The browser app runs the scripts of a
mockup the agent showed; the desktop app, and the browser until the mockup is shown, render the same file
with no script. So the clause must be true in both, and it asks for a mockup that is complete without
scripts:

- write a self-contained HTML file in the scratch dir, link `thinkrail-theme.css` with a
  relative href (not copy it in) and read it for token names, colour with its tokens and leave the page
  background to the theme, inline all data and images, draw a dialog, drawer, toast or open dropdown in
  normal flow or give `body` a pixel `min-height` (a `position: fixed` layer adds no height, so a
  fixed-only dialog would get the 120 px minimum and be cut off; an absolutely positioned panel that opens
  after load is not measured either), and no `vh` or `height: 100%` on `html`/`body` (a document sized
  from its frame keeps the bounded card);
- some clients run no script and load nothing from a URL: there scripts and handlers are removed, a CDN
  file does not load and a `<form>` is dropped with everything in it. So controls go directly in the page
  with no `<form>`, all the mockup's own CSS is in the file (a CDN stylesheet would style it in the browser
  and leave it unstyled on desktop, so a CDN file may only add what a script draws), and anything a script
  draws has a static version as normal markup that the script replaces when it runs. The clause forbids
  `<noscript>` for that version: the themed frame shows it, but where scripts run it never renders, also
  when the library does not load (offline, a proxy), and the card would be empty;
- where scripts run, inline scripts and handlers work and a library loads only from the CDN prefixes,
  with an exact version (the text lists `MOCKUP_CDN_SOURCES`; with an empty list it says no library loads
  from a URL);
- not to use fetch, XHR, WebSocket, workers, `eval`, `new Function`, `localStorage`, cookies, `alert`, form
  submit, links, navigation or `document.write` after load (blocked, or they close the mockup);
  WebAssembly only from inline bytes;
- not to call `history.pushState` or set `location.hash` (no hash router, no hash tabs): nothing blocks
  them, and each call adds an entry to the app tab's history;
- not to call `scrollIntoView()`, to call `focus()` only in a handler of a user action, and not to cancel
  the Tab key: nothing blocks them, in Chromium the first two move the chat transcript to the mockup, and
  a cancelled Tab keeps the keyboard inside the frame;
- a script that reads token colours redraws on the window's `thinkrail:themechange` event.

The list of blocked things is an instruction, not a promise of isolation:
[[module-resource-renderers]] *Known limits of a scripted frame* says what a hostile mockup can still do.
The clause was checked in Chromium, WebKit and the macOS desktop app; WebView2 and WebKitGTK were not
run.

The host composes this descriptor from the server registry ([[submodule-server-extensions]]); a strict
validation call through that composition is pinned in `packages/server` (dev) and in the artifact probes
(CLI binary and desktop), so the vanilla probe can never be what runs in ThinkRail.

## Rendering contract (web)

Diagrams, comparison options and recommended choices preserve the existing chat presentation. A
completed `type: "file"` call renders `FileCard`: the title, the `before → path` links (through
`onOpenFile`), and [[module-resource-renderers]]' `FramedResourcePreview` for the path and `before` — the
same renderers, diff and review comments as diff review. The card frame is a 480px box (Monaco and
bounded diffs need a height) with `fitContent`: an HTML mockup under the scratch dir, alone or as a
before/after comparison of two mockups, grows the card to its content height (rendered box 120–1600 px,
Fill width unless the user picks another) and takes the app's live theme, while code, images, other diffs,
HTML outside the scratch dir and a mockup sized from its frame (`100vh`, `height: 100%`) keep the bounded
box. In a browser the mockup a finished call showed (`path` and `before`) also runs its own scripts, in a
sandboxed frame; in the desktop app, and for a file under the scratch dir that no call showed, no script
from the file and none from ThinkRail runs and the file gets the theme and nothing more; a script that a
native webview injects into frames is not covered ([[module-resource-renderers]], *Themed frame* and
*Scripted frame*; [[module-web]] owns the rule). Its toolbar adds **Open in tab** (`host.openFile` keep, or
`host.openComparison` for a before/after) and **Full screen** (a dialog rendering the same preview with
Split/Inline; renderer choice and view state, such as the HTML preview width, are shared with the card).
The frame and its actions live in the SDK because the questionnaire's previews use the same one. A card always shows the file's
**current** content, never a snapshot from the tool call: editing a mockup updates every card that shows it
(review comments follow the file). A mockup deleted under a mounted card leaves it on its last loaded version
under a "Couldn't refresh" notice; a card mounted afterwards shows the load error. That is the price
of anchoring review to real files; the tool guideline asks the agent to keep an earlier proposal as a copy
passed as `before` when it should stay visible. The workspace and chat come from `useResourceScope`, which the chat transcript provides to
its rows, so review sends land in the chat that shows the card; with no host or scope (a subagent transcript)
the card shows only the links. The
registration is primary and expanded by default; its title or diagram/comparison/file summary is available
without rendering. Invalid or streaming arguments remain defensive and tool errors preserve readable
result text.

`MermaidView` derives mermaid's strict-mode theme from the host's CSS variables and re-renders after a
completed `data-theme` swap, or after a font settings change that moves the code family (resolved from
`.tr-code-block` through `@thinkrail/ui/fonts`' `watchFont`, re-rendered once that face has loaded) or a
change to the custom face set, which can change a family's metrics without its name; weight-only changes do
not re-render, and only the latest render applies. Every render, the first included, waits for the code face
to load, so a cold custom font never leaves labels sized for the fallback. It pins `look: "classic"` and `layout: "dagre"`: mermaid 12's defaults add node glow
shadows and orthogonal edges, which clash with the app's flat surfaces, and re-lay out existing diagrams. It supports a caller-supplied loading fallback, a fullscreen Dialog, and
pan/zoom controls. The fullscreen canvas owns modifier-wheel zoom and WebKit gesture pinch from its
local gesture-start baseline so desktop page zoom does not claim the gesture. Renderer failure shows
the error and a plain source block matching the app CodeBlock's unhighlighted branch; it never imports
the app's chat highlighter. `args` and pan/zoom math retain focused unit coverage.
